# 小白开发搭子：新手使用指引

**Newbie Dev Buddy** 帮你把“想做什么”变成可讨论、可保存、可继续的开发过程。你负责目标和取舍，AI 负责阅读代码、准备技术材料和执行；AI 应把方案讲清楚，方便你提出意见和确认开发。

在 Codex 中调用 **`$newbie-dev-buddy`** 开始；Claude Code 与 DeepSeek Harness 使用 `/newbie-dev-buddy`，pi 使用 `/skill:newbie-dev-buddy`。其他助手见[宿主支持](agent-support.md#host-paths-and-invocation)。

## 1. 开始前准备三件事

- 一个支持本地 Skill、能操作项目文件的 AI 编程助手，例如 Codex、CodeBuddy 或 OpenCode。
- 已安装的 `newbie-dev-buddy` Skill；安装方法见[中文说明](../README.zh-CN.md#要求与安装)。已有安装无需重复安装；由 Skills Manager 管理的，通过原管理器更新。
- 一个打开或新建的项目文件夹，并明确告诉 AI 这是本次项目目录。

让 AI 先检查环境是否可用：核心工具需要 Python 3.9 及以上，当前扫描支持 macOS/Linux。这个 Skill 不自带 AI 模型，也不自动配置开发环境。Windows 建议在 WSL 内准备整套工具，不混用两边路径。搭子安装已包含 Acceptance Kit 运行时，不需要另装 Kit Skill；验收仍可选，仅运行 `run-checks` 或 `verify` 时需要 Node.js 22+。安装不会自动运行检查、安装 Node/npm 或启动服务。

你不必填写 JSON、版本编号或 SHA，也不必照着敲命令，这些由 AI 准备。

尚未安装时，把本项目的 GitHub 仓库地址一起发给助手：

```text
请从[本项目的 GitHub 仓库地址]安装“小白开发搭子”Skill 到[我使用的助手]。
先检查是否已有安装；如果由 Skills Manager 管理，就通过管理器更新。
先预览所选宿主的基础安装，不修改其他助手。
完成后告诉我正确的调用方式，以及助手是否已实际发现这个 Skill。
```

### 选择基础版还是增强版

基础版已经可以读源码、讨论模块、保存方案和历史。增强版多了 CodeGraph 结构分析，适合已有代码较多、调用关系较复杂的项目；它不会替你判断业务模块是否合理。

让 AI 这样准备即可：

```text
请使用本工具的安装器，为[我使用的助手]准备增强安装。
先检查已有 CodeGraph，展示要安装到哪里、MCP 配置改哪里；
不覆盖不同的已有安装、不升级现有工具、不放宽权限。
配置若要手动应用，请给出候选文件和宿主操作步骤。
安装后区分文件就绪、配置应用、工具连接和模型实际调用；
先不要给我的项目建索引，首次使用时再核对项目范围和排除项。
```

增强版只准备工具和连接信息。部分助手还需要加载候选配置、启用项目 MCP 或重新加载；安装器不能代替这些宿主步骤。CodeGraph 暂时不可用时，可继续基础流程，并明确结构分析的缺口。具体说明见 [CodeGraph 接入](codegraph.md)。

下面提示词以 Codex 的 `$newbie-dev-buddy` 为例，使用其他助手时替换为对应调用方式。

## 2. 新项目：先确定第一版做什么

用日常语言描述用途、使用者和希望得到的结果。AI 应先收敛最小需求，再说明各模块的职责、输入输出、配合关系和完成标准。你看不懂的地方可以要求换一种说法；不想做的功能可以删掉。

复制到助手中，把方括号里的内容换成自己的描述：

```text
$newbie-dev-buddy
项目目录：[我选定的项目文件夹]
我想做：[工具用途、谁使用、希望得到的结果]。
我不懂编程，请先帮我确定第一版最少需要哪些功能，
说明模块各自做什么、接收和输出什么、怎样配合，以及怎样判断完成。
先展示方案，等我确认后保存初始结构，再逐项提出开发方案并实施。
```

确认时说清接受哪个版本，例如：“我接受你刚展示的第 1 版模块结构。”AI 随后保存结构；计划中的模块不会因此变成“已开发”。开发方案也需要确认，之后 AI 才开始实施并记录结果。

## 3. 已有项目：先弄清现在是什么

已有代码时，让 AI 先扫描并核对源码，按职责整理候选模块地图。它应区分已核实、推断和待核实的内容，说明没读到哪些文件、现有测试检查了什么。扫描清单本身不能自动判断业务模块。

```text
$newbie-dev-buddy
项目目录：[已有项目的文件夹]
请先梳理这个项目现在有哪些模块、各自负责什么、怎样联系。
区分已核实、推断和待核实，列出未覆盖部分和现有测试情况。
先给我候选地图，确认后再保存正式结构；架构调整另提方案。
```

## 4. 后续修改：讲清变化和完成条件

```text
$newbie-dev-buddy
请在这个项目增加或修改：[具体需求]。
先读取模块结构和旧修改记录，说明会影响哪些部分、准备怎样改、
怎样判断改对了，并列出可选检查。展示具体方案，等我确认后实施。
完成后告诉我实际改了什么、检查了什么，还有什么没验证。
```

如果新要求改变了原方案的范围或接口，AI 应保存当前进展，修订方案后再确认。旧方案和旧理由保留，便于以后知道为什么这样做。

## 5. 模块说明怎样核对

打开 `docs/newbie-dev-buddy/MODULES.md`，先看“项目分工”，再看各模块负责什么、需要遵守什么约定、怎样检查。它说明已经确认的安排，不代表功能完成或检查通过。

你可以直接告诉 AI：“这个部分还应该负责……”“这条约定是什么意思？”AI 应先解释、整理修改建议，确认后更新文档并保留旧版。另一份 `MODULES.json` 给工具读取，你不必编辑它。两份文档由工具一起保存；直接在 MD 写的意见会先保留，不会自动成为已接受变更。

## 6. Acceptance Kit 怎么选

Kit 运行项目已有的检查配置；它不会凭空补齐测试。默认使用内置版本，不需要填 `--kit`；如已有可信兼容的外部 Kit，也可显式指定。先按[配置文档](../vendor/acceptance-kit/docs/configuration.md)准备真实配置和测试，请 AI 解释准备运行的检查内容，再选择：

| 选择 | 适合怎样使用 |
|---|---|
| 手动（`manual`） | 本次由你决定要不要检查，不自动成为交付必需条件。 |
| 随修改（`on-change`） | 涉及这个模块时进入检查计划，按已确认的策略运行。 |
| 必须通过（`required`） | 涉及这个模块时，必需检查及相关已配置接口检查通过，才满足已有的交付条件。 |

可以告诉 AI：“先用手动检查，请解释检查内容和现有配置；我选定后再运行。”模块之间交换信息的流程，也可能需要一起检查。

**未配置、未检查、只检查了一部分，都不能当作通过。** 不启用验收、缺少运行环境或测试时，照样可以保存方案和实施记录，但应保留待验项。以前通过的结果也可能因代码变化而失效；AI 需复核，不能直接沿用。检查通过只说明实际检查的范围，不能保证全部功能或架构都正确。

任何已运行检查失败或过期，已有交付门槛就不能算满足；没有必需检查也不代表全项目通过。

## 7. 下次继续，或换一个对话

继续旧会话也要让 AI 读记录；换对话时，重新指定同一个项目目录：

```text
$newbie-dev-buddy
请继续这个项目。先检查 MODULES.json 与 MODULES.md 是否一致，读取模块数据、
相关修改方案和 .handoff/newbie-dev-buddy/ 中的实施记录，核对当前状态。
告诉我已完成、未完成、待验证的内容和下一步，再继续已确认的范围。
```

`docs/newbie-dev-buddy/` 保存结构和已接受方案；`.handoff/newbie-dev-buddy/` 保存扫描、历史、决定和执行记录。两处一起备份，后者也不是可以随手删除的缓存。分享记录前检查其中是否含私密信息。

## 几个常见词

**模块**是负责一类工作的部分；**依赖**表示一个部分需要另一个部分的结果；**接口或契约**是彼此交换信息、处理数据时遵守的约定；**验收**是用具体操作和结果判断需求是否完成。

当前版本仍属实验工具。它帮助保存开发过程，不自动证明架构合理、测试充分，也不负责一键上线。
