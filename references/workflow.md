# 模块结构、方案修订与实施记录

## 项目进入

沿用项目规则和可靠的领域流程，把必要证据连接到模块方案，不重复建立另一套调研或实施体系。

既有项目先梳理现状，再提出结构；详细方法见 [discovery.md](discovery.md)。新项目先提出职责、路径、依赖和契约，也可直接使用已有已确认结构的 `init` 入口。不能把开始讨论当作接受结构，不能把目标架构写成已经实现。

地图接受与代码修改是不同动作。整理模块默认记录现状；需要拆分实现、迁移接口或调整依赖时，另提修改方案。模块名、路径变化保留 ID；拆分、合并、退休在地图候选中保存对应关系，旧 ID 不用于其他职责。

## 持久化材料

| 位置 | 角色 |
|---|---|
| `docs/module-change/MODULES.md` | 当前确认的模块、关系、契约及可选验收配置 |
| `docs/module-change/changes/` | 已接受的具体修改版本 |
| `.handoff/module-change/discovery/` | 扫描清单、来源指纹及覆盖记录 |
| `.handoff/module-change/maps/drafts/`、`maps/accepted/` | 地图候选及接受版本 |
| `.handoff/module-change/maps/rejected/`、`maps/history/` | 地图拒绝决定及旧总览完整内容 |
| `.handoff/module-change/drafts/` | 修改候选与修订 |
| `.handoff/module-change/decisions/` | 拒绝决定 |
| `.handoff/module-change/records/` | 实施、中断与验收事件 |
| `.handoff/module-change/CURRENT.md`、`HISTORY.md` | 派生导航索引 |

具体路径以命令返回为准，不能删除记录后靠索引恢复。

模块总览和方案 Markdown 用 JSON 对象作为合法 YAML frontmatter；结构字段与正文共同构成文档。输入 JSON 是 CLI 传输材料，不再维护第二份相互竞争的权威 JSON。需要更新已接受地图时使用地图修订；需要更新已接受方案时新建方案修订。

备份同时保留 `docs/module-change/` 和 `.handoff/module-change/`。只有导航索引可重建；从 Kit 输入排除记录目录不等于从备份排除。

## 提出修改

执行 `status`，读当前地图、适用旧方案、实际代码与事件，然后确定：

- 主模块及提供输入、依赖输出、共享数据或接口的关联模块。
- 稳定功能或接口名，必要时附路径，不仅写易变化的行号。
- 继续适用、需要替换的旧约束，以及当前实现和文档的差异。
- 完整方案、影响、重要取舍和可观察的验收条件。
- 本次需要的模块检查、集成检查、配置与未覆盖项。

依赖图给出的关联模块不是完整影响证明。配置、跨进程调用、动态导入及人工流程可能需要补充核查；具体缺口应写清楚。

`propose` 保存完整候选，同时冻结验证计划和相关输入。向用户展示一致的版本及其 ID、修订号。用户接受后，以该候选完整 Markdown SHA 执行 `decide`。拒绝保存理由；修订保存完整新版本并重新展示。决策说明记录实际发生的确认，不自行产生授权。

接受前校验 digest、最新修订和基线；遇到源码、配置或地图漂移，查明变化，再生成必要的新候选。不能只换 digest 绕过确认。

## 同位置新修改

使用 `supersedes` 指明旧 `change`、`revision` 和具体替换的 `scope`，保留未替换约束。更高修订被接受或旧方案被替换后，旧版保留为历史，不能继续执行或验收。

接受新方案时，代码可能仍是旧行为。记录分别说明适用方案、实际实施和当前证据。地图更新也不会自动更新旧方案的路径范围、验证计划或历史通过。

## 实施与恢复

获取接受后 Markdown 的 digest，执行 `record --event started` 后修改。在已接受范围内自主完成必要实现和调试；实质新增功能、模块、接口或数据语义、改变预期结果或验收条件时，保存 `interrupted` 记录，再修订并确认。

中断说明包含已改文件、实际行为、未完成部分及恢复步骤。下一次从记录和当前文件核对后继续；开始、实施事件是执行者声明，需要检查实际产物。

源代码、模块契约和计划产物完成后执行 `record --event implemented`。模块结构需要变更时用 `map-propose` 与 `map-decide` 保留旧图；不要重新初始化覆盖历史。更新地图后重新检查正在执行的方案与验收输入，旧指纹不能代表新结构。

## 可选模块验收

按 [verification.md](verification.md) 配置模块和集成检查。先核对 Kit、配置与命令；用户选择检查或已确认策略授权后，`run-checks` 实际运行选中的 Kit 配置。已有报告用 `verify --check-id` 复核覆盖；兼容的无 `--check-id` 入口只保存整体验证记录。

先完成代码、文档、配置和测试，再运行验收。配置应排除生成的 `.handoff/module-change/` 或 `.handoff`，保留相关代码和文档。工具不会为通过而自动扩大排除范围。

失败、缺失、过期和检查器错误如实记录。不伪造 Kit 报告、不把未启用算通过、不把单模块通过当作集成通过。`status` 不调用 Kit；复用历史结论前再次 `verify`。

收尾分别报告方案、实施、各项检查和剩余缺口，给出实际文档及报告位置。`delivery_ready` 是当前必需检查证据门槛，不证明需求、架构或整体项目质量充分。

命令与字段见 [cli.md](cli.md)。
