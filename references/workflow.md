# 模块结构、方案修订与实施记录

## 项目进入与模块结构

先遵循项目已有规则。已有可靠领域流程时，沿用其证据标准、实现方式与验收方法；把该流程需要的结果连到本次模块方案中，避免重新建立一套重复流程。

新项目先提出结构方案，包括模块职责、路径、依赖及契约，再让用户接受、修订或拒绝。接受后才用 `init` 保存模块总览。初始化输入的决策说明应记录用户接受的是哪份结构方案及其内容，不把“开始讨论”解释为已接受结构。

既有项目不能仅靠目录名或旧文档推断模块。核对实现中的职责、入口、调用关系、跨模块接口与数据流，指出旧文档与实现的差异，再提出结构方案。无法核实的部分明确标为待核实；不要把设计目标写成已实现状态。

模块结构保存在 `docs/module-change/MODULES.md`。每个模块至少有稳定 ID、名称、职责、路径、依赖和契约。`depends_on` 表示该模块依赖哪些模块。模块名称与文件位置可以变，ID 不因重命名或移动而更换，也不应重新用于不同职责。新项目允许列出尚未创建的路径。

拆分或合并模块时，在已确认方案及总览正文中说明新旧 ID 的对应关系和职责迁移。CLI 不自动决定拆分或合并；它校验模块引用与路径。

例如，一个合成导出项目可使用：

| 模块 ID | 职责 | 依赖 | 契约要点 |
|---|---|---|---|
| `M-INGEST` | 读取结构化输入 | 无 | 输出字段与缺失值含义 |
| `M-EXPORT` | 生成导出文件 | `M-INGEST` | 列顺序、编码与格式 |
| `M-CLI` | 接收命令行参数 | `M-EXPORT` | 参数默认值与退出码 |

不要把每个文件都拆成一个模块。选能帮助定位职责、接口和影响的边界；若现有模块足以表达需求，沿用它。

## 持久化文件的角色

| 位置 | 角色 |
|---|---|
| `docs/module-change/MODULES.md` | 当前模块结构与契约 |
| `.handoff/module-change/drafts/` | 候选方案、修订及拒绝历史 |
| `docs/module-change/changes/` | 已接受的具体方案版本 |
| `.handoff/module-change/records/` | 实施、实施中断及验收事件 |
| `.handoff/module-change/CURRENT.md` | 从上述材料生成的当前状态索引 |

模块总览与方案 Markdown 使用 JSON 对象作为合法 YAML frontmatter。frontmatter 中的稳定 ID、关系及正文一起构成权威内容；不要同时维护另一份相互竞争的 JSON 权威方案。输入 JSON 只是 CLI 的输入材料。

接受后保留该版本；要改变方案就新建修订，不能改写旧版以制造“原本就接受了”的印象。执行或验收的后来事实写入事件记录。`CURRENT.md` 用于导航，不覆盖旧版历史，也不单独证明实际实现。

`.handoff/module-change/` 包含需要长期保存的草案、拒绝决定和执行事件，不是可整目录删除的缓存。只有 `CURRENT.md`、`HISTORY.md` 索引可重建；备份应同时保留 `docs/module-change/` 和这些记录。从 Kit 输入排除不等于从项目备份排除。

同一变更的更高修订被接受，或旧版本被其他已接受方案通过 `supersedes` 替换后，旧版本保留为历史，不再对其执行 `record` 或 `verify`。部分旧约束继续适用时，将这些约束带入当前方案并据当前版本实施。

## 从需求到候选方案

每次需求先执行 `status` 并阅读相关材料，然后完成以下定位：

- 主模块：需求主要改变哪项职责。
- 关联模块：谁提供输入、依赖该输出，或共享相关接口与数据约定。
- 修改位置：稳定的功能或接口名，必要时附具体路径；不要只写可能变化的代码行号。
- 旧约束：目前适用的模块契约、已接受方案及其实施状态。
- 修改方案：具体行为、影响、关键取舍及可观察的验收条件。

工具返回的关联模块是检查候选，不证明所有影响都已找到。需要结合当前实现核实调用、数据流、配置及相关用户行为。对尚未核实的影响，说明具体缺口。

用 `propose` 保存完整候选。向用户展示与版本一致的方案，标明变更 ID 和修订号，并提供接受、修订或拒绝的选择。展示后文件内容若改变，须重新查看和确认，不能继续使用旧 digest。

用户意见对应三种处理：

- 接受：确定用户接受的具体版本、保存决策说明，再用该候选的 SHA 执行 `decide --decision accept`。
- 修订：把意见纳入新的完整方案，再次 `propose`；再次展示并等待接受，不沿用前一版本的接受。
- 拒绝：保存拒绝理由，再用该候选的 SHA 执行 `decide --decision reject`；不实施被拒绝版本。

简短的“可以”“继续”需要结合上下文对应到刚刚展示的具体版本。它不能扩展成新增功能、扩大范围或接受尚未展示的修订。CLI 保存代理记录的决策，不能核实这段人类同意是否真实。

## 替换旧方案与保持当前状态

同一功能可以发生多次修改。新方案应指出替换哪个旧方案版本的哪个范围，而非仅写“使用最新方案”。使用 `supersedes` 保存 `{change, revision, scope}`，并在正文解释新行为与继续有效的旧约束。

例如，已接受 `C-001` 修订 1 规定“导出 `item_id` 与 `score` 两列，使用 UTF-8”。后来的 `C-002` 修订 1 只把默认列顺序改成 `score`、`item_id`，可写：

```json
"supersedes": [
  {
    "change": "C-001",
    "revision": 1,
    "scope": "export.write_table 的默认列顺序；保留两列字段及 UTF-8 编码约束"
  }
]
```

仅接受新方案时，当前实现可能仍处于旧行为。状态记录必须分别说明当前适用方案、实际已完成实施和当前验收情况。接受、实施、验收各自更新，不能互相代替。

模块边界、职责或契约需要改变时，把变化写进此次方案；用户接受后先记录 `started`，再更新模块总览与代码，并保留旧约束的替换说明。完成后用 `refresh` 更新派生索引。不要为修订重新初始化项目或覆盖历史。

## 接受后的实施

接受前的检查包括候选的完整 Markdown digest、该变更的最新修订和项目基线。检查失败时先查明差异；项目被他人修改、模块文档漂移或版本已更新，不能直接用新 digest 重试当作确认未变。

接受成功后，从命令结果或状态获取已接受 Markdown 的 SHA。修改代码前，对该版本执行 `record --event started`，记录将实施的具体范围与必要前提。

已接受范围内的实现细节、必要调试和已有验收可自主推进，不需要每一步重新询问。以下情况需要修订后再确认：

- 增加原方案未包含的功能、模块或实质范围。
- 改变接口、参数语义、字段或持久化数据约定。
- 改变用户原先接受的预期结果、重要取舍或验收条件。

发现上述变化时，先用 `record --event interrupted` 保存已改文件、实际现状、未完成部分及恢复步骤，然后提出修订。不要把代码中已经做出的扩展当作用户已经接受。

因会话中断或环境问题停止时，同样保存中断说明；下一次工作从记录和当前文件核对后恢复。记录的“已开始”或“已实施”是执行者声明，仍需检查实际文件与证据。

完成源代码、相关模块文档及计划内产物后，执行 `record --event implemented`。说明实际变更、差异、尚未验证范围与接下来的验收入口。不要在源代码尚未完成时提前记录实施完成。

## 验收与可信边界

先按项目可靠的既有 Acceptance Kit 流程实际运行验收，得到项目内真实报告，再调用 `verify`。它调用 Kit 的 `check` 核对报告是否当前并登记结果；它本身不运行测试，也不证明验收条件足以覆盖整个需求。

`status` 只显示历史验收结果以及输入和报告文件的指纹，不调用 Kit。即使显示以前通过，也需要留意 `receipt_recheck_required`，继续使用验收结论前再次执行 `verify`。

Kit 输入需要排除生成的 `.handoff/module-change/`，否则 `verify` 写入验收记录可能使输入指纹改变。不要为了消除过期状态排除整个 `docs/`，源代码和模块文档应先完成再运行 Kit。工具不会自动修改 Kit 配置；缺少必要排除时先按项目授权范围配置，超出范围则说明所需变更。

只有真实、当前且符合 Kit 检查的报告才能记录通过。报告失败、过期、缺失或检查错误都如实处理。没有 Kit 时可以保留执行说明、观察结果和待验项，但不能生成冒充 Kit 报告的 JSON，也不能写虚假的 pass。

收尾说明分别报告方案、实施和验收状态，给出权威文档、实施记录及报告位置。检查通过仍不等于完整安全认证，也不等于 AI 已被证明正确理解全部需求。

需要命令、输入字段和合成示例时，读 [cli.md](cli.md)。
