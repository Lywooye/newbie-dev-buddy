# 模块结构、方案修订与实施记录

## 项目进入

沿用项目规则和可靠的领域流程，把必要证据连接到模块方案，不重复建立另一套调研或实施体系。

既有项目先梳理现状，再提出结构；详细方法见 [discovery.md](discovery.md)。新项目先提出职责、路径、依赖和契约，也可直接使用已有已确认结构的 `init` 入口。不能把开始讨论当作接受结构，不能把目标架构写成已经实现。

地图接受与代码修改是不同动作。整理模块默认记录现状；需要拆分实现、迁移接口或调整依赖时，另提修改方案。模块名、路径变化保留 ID；拆分、合并、退休在地图候选中保存对应关系，旧 ID 不用于其他职责。

## 持久化材料

| 位置 | 角色 |
|---|---|
| `docs/newbie-dev-buddy/MODULES.json` | 当前确认的完整模块数据：职责、关系、约定及可选验收配置 |
| `docs/newbie-dev-buddy/MODULES.md` | 从 JSON 生成的可读模块说明，用于用户核对 |
| `docs/newbie-dev-buddy/changes/` | 已接受的具体修改版本 |
| `.handoff/newbie-dev-buddy/discovery/` | 扫描清单、来源指纹及覆盖记录 |
| `.handoff/newbie-dev-buddy/maps/drafts/`、`maps/accepted/` | 地图候选及接受版本 |
| `.handoff/newbie-dev-buddy/maps/rejected/`、`maps/history/` | 地图拒绝决定及旧总览 MD/JSON 原文 |
| `.handoff/newbie-dev-buddy/maps/repairs/` | 重建视图前保留的 MD/JSON，包括用户手写意见 |
| `.handoff/newbie-dev-buddy/drafts/` | 修改候选与修订 |
| `.handoff/newbie-dev-buddy/decisions/` | 拒绝决定 |
| `.handoff/newbie-dev-buddy/records/` | 实施、中断与验收事件 |
| `.handoff/newbie-dev-buddy/CURRENT.md`、`HISTORY.md` | 派生导航索引 |

具体路径以命令返回为准，不能删除记录后靠索引恢复。

当前模块数据只以 `MODULES.json` 为准，`MODULES.md` 是生成的阅读版本。两者来自同一次保存，MD 含 JSON 原文指纹；正常读取时核对完整生成内容。地图接受同时更新两份文件、保留旧版，不靠 AI 分别改写。输入 `map-json` 是候选传输材料，不能当成另一份当前地图。方案、决定和事件 Markdown 继续使用原有 JSON frontmatter，历史原文不转换。结构调整走地图修订；已确认开发方案内的职责/约定更新，在实施收尾时同步并保留旧图。

备份同时保留 `docs/newbie-dev-buddy/` 和 `.handoff/newbie-dev-buddy/`。只有导航索引可重建；从 Kit 输入排除记录目录不等于从备份排除。

## 模块文档同步与恢复

给用户看 `MODULES.md`，助手读取完整 `MODULES.json` 并先运行 `status`。独立结构调整使用 `map-propose` / `map-decide`。本次功能修改已包含并确认的职责/约定，通过 `documentation.map_updates` 在实施收尾时保存；不要直接编辑当前 JSON，也不要只更新阅读版本。JSON 与 MD 一致只代表两份文件对应，不能证明内容已跟上源码。

- **两份文件不一致：** 暂停以它们为依据的后续操作，核对修改来源。用户在 MD 中的意见先保留为候选，不能被重建命令自动接受。
- **重建阅读版本：** `map-render --expect-digest JSON_SHA` 从选定 JSON 重建 MD。现有不一致 MD 和 JSON 先保存在 `maps/repairs/`；缺少 MD 也可重建。它不改变 JSON、不接受业务修改、不运行测试。指纹不匹配则拒绝操作。
- **旧项目转换：** 仅有原格式 `MODULES.md` 的项目仍可使用。确认转换时，以旧 MD 的完整 SHA 调用 `map-migrate`，保留原 MD 原文，生成完整 JSON 和可读 MD。仅转换格式，不改职责和约定。转换后原方案或报告跟踪的文档可能变化，需要重新评估或重验，不能换指纹冒充原证据仍有效。首次接受新地图也会采用新格式并保留旧图。
- **写入中断：** 每个文件用临时文件替换，普通写入失败尝试恢复原文件；跨文件保存不保证断电时同时完成。若进程中断，先核对当前文件、历史、决定和锁。同步检查可以发现不一致，不会擅自选择哪个版本正确。

旧修改方案和历史报告保留原文；新地图不扩大旧方案范围。旧版尚未接受的地图候选如不符合当前生成模板，应重新提出并展示，不能直接换 digest。

## 提出修改

执行 `status`，读当前地图、适用旧方案、实际代码与事件，然后确定：

- 主模块及提供输入、依赖输出、共享数据或接口的关联模块。
- 稳定功能或接口名，必要时附路径，不仅写易变化的行号。
- 继续适用、需要替换的旧约束，以及当前实现和文档的差异。
- 完整方案、影响、重要取舍和可观察的验收条件。
- 本次需要的模块检查、集成检查、配置与未覆盖项。
- 需要更新的项目文档、正式地图中应替换的职责/约定原文；保持原图时说明理由。文档同步与功能修改一起确认。

依赖图给出的关联模块不是完整影响证明。配置、跨进程调用、动态导入及人工流程可能需要补充核查；具体缺口应写清楚。

`propose` 保存完整候选，同时冻结验证计划和相关输入。向用户展示一致的版本及其 ID、修订号。用户接受后，以该候选完整 Markdown SHA 执行 `decide`。拒绝保存理由；修订保存完整新版本并重新展示。决策说明记录实际发生的确认，不自行产生授权。

接受前校验 digest、最新修订和基线；遇到源码、配置或地图漂移，查明变化，再生成必要的新候选。不能只换 digest 绕过确认。

## 同位置新修改

使用 `supersedes` 指明旧 `change`、`revision` 和具体替换的 `scope`，保留未替换约束。更高修订被接受或旧方案被替换后，旧版保留为历史，不能继续执行或验收。

接受新方案时，代码可能仍是旧行为。记录分别说明适用方案、实际实施和当前证据。地图更新也不会自动更新旧方案的路径范围、验证计划或历史通过。

## 实施与恢复

获取接受后 Markdown 的 digest，执行 `record --event started` 后修改。在已接受范围内自主完成必要实现和调试；实质新增功能、模块、接口或数据语义、改变预期结果或验收条件时，保存 `interrupted` 记录，再修订并确认。

中断说明包含已改文件、实际行为、未完成部分及恢复步骤。下一次从记录和当前文件核对后继续；开始、实施事件是执行者声明，需要检查实际产物。

源代码与计划文档完成后，按下节提供收尾材料，再执行 `record --event implemented --completion-json FILE`。工具不会替助手编写项目开发或排障文档，必须先更新这些文件。模块结构调整仍用地图候选；不要重新初始化覆盖历史。更新地图可能使其他方案或旧验收输入过期，不能换指纹冒充原证据。

## 文档收尾与修改时间

新候选必须包含 `documentation`。助手核对每条行为或规则变更，在 `map_updates` 中给出完整替换文字，只允许本次主/关联模块的 `purpose` 与 `contract`；不是往过时约定后面追加相反文字。ID、路径、依赖和检查配置不由收尾改动。`map_reason` 解释为什么更新或保留地图；`files` 列出应核对的项目文档，不列自动生成的搭子材料。用户不需要手写这些字段。

完成时，`completion-json.files` 的路径和具体说明必须覆盖开始记录以来所有实际变化的跟踪文件，不能多报或漏报。声明的项目文档未改变时，必须在 `reviewed_documents` 中解释为什么现有文字仍准确。文件内容的语义对应、范围是否完整仍需助手阅读源码核对；声明与指纹检查不能替代它。

收尾保存旧地图原文，在已接受范围内同步 JSON/MD、递增地图版本，追加具体记录：逐文件说明、修改前后 SHA-256、模块约定前后文字及文档核对理由。此类版本来源是已接受开发方案和收尾事件，不另造一份地图确认。地图与各更新模块标注同步时间，并指向修改记录；交接索引显示最新记录时间和链接。普通写入失败尝试恢复地图；进程崩溃仍需按同步与恢复规则核对锁、历史与当前文件。

时间均使用 UTC：开始事件的时间、完成/补记事件的时间、文档同步时间由工具当时生成。文件系统修改时间另存为观察值，可能因复制或恢复改变，不能作为可靠作者或修改发生时间。旧记录没有开始时的文件时间就留空；不要根据本次同步时间伪造历史改动时间。

0.6 及更早版本的已实施方案缺少 `documentation_plan` 时，先核对旧接受内容及当前代码，再用 `record --event documented --completion-json FILE` 追加补记。材料额外包含 `documentation`，仅登记旧方案主/关联模块范围内已授权的职责/约定与文档修正；新增决策仍需新方案。必须有原开始和实施记录，保留原接受版本、实施时间和事件字节，补记时间为现在。不将旧方案改造成新版计划，也不把历史未核对事项默认算完成。

`status.documentation.state` 区分 `pending`、`legacy_unreviewed`、`synced`、`needs_review`。`handoff_ready` 要求已实施、文档收尾完成且跟踪输入未漂移；它不代表测试通过。新一轮实施或新的内容漂移会清除可交接状态。旧方案尚未补记时，可以继续读取历史，但不能声称完整交付。

## 可选模块验收

按 [verification.md](verification.md) 配置模块和集成检查。先核对 Kit、配置与命令；用户选择检查或已确认策略授权后，`run-checks` 实际运行选中的 Kit 配置。已有报告用 `verify --check-id` 复核覆盖；无 `--check-id` 时只保存整体验证记录。

先完成代码、文档、配置和测试，再运行验收。配置应排除生成的 `.handoff/newbie-dev-buddy/` 或 `.handoff`，保留相关代码和文档。工具不会为通过而自动扩大排除范围。

失败、缺失、过期和检查器错误如实记录。不伪造 Kit 报告、不把未启用算通过、不把单模块通过当作集成通过。`status` 不调用 Kit；复用历史结论前再次 `verify`。

收尾分别报告方案、实施、各项检查和剩余缺口，给出实际文档及报告位置。`delivery_ready` 是当前必需检查证据门槛，不证明需求、架构或整体项目质量充分。

命令与字段见 [cli.md](cli.md)。
