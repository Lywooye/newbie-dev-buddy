# 可选模块与集成验收

## 配置和策略

核心 CLI 不包含 Kit。使用可信的现有 Acceptance Kit；模块配置只是选择它的原有配置和步骤，不向 Kit 配置添加本工具专属字段。

地图可设置 `verification_defaults.policy`；每个模块可用 `verification.policy` 覆盖：

| 策略 | 含义 |
|---|---|
| `manual` | 按本次选择运行，不自动视为交付必需 |
| `on-change` | 受本次修改影响时进入检查计划，依据已确认策略运行 |
| `required` | 受本次修改影响时成为交付证据门槛 |

策略本身不提供测试。有配置时给出项目内 `config` 路径、非空 `steps` 和非空 `inputs`；输入应包含能反映实际覆盖的源码、配置、测试和必要数据。使用恰当的路径或目录，不把无关私人文件放进检查输入。

模块检查 ID 为 `module:M-ID`；跨模块检查放在 `integration_checks`，ID 为 `integration:ID`，至少引用两个模块，策略为 `on-change` 或 `required`。它们说明哪些接口或流程需要联动检查，不能用几个独立模块报告代替集成验证。

Kit 配置必须在 `exclude` 中排除 `.handoff/newbie-dev-buddy` 或整个 `.handoff`，JSON 路径不要带末尾斜线，否则登记结果会改变报告输入。不要排除所有 `docs/`；工具不自动改 Kit 配置。具体 Kit 的配置格式与可执行步骤按该 Kit 文档核对。

## 冻结与执行

`propose` 从当前地图冻结本次模块与集成检查计划，包括配置 SHA 和完整 JSON 快照、步骤及声明输入。有配置时，配置、声明源码和测试必须先存在且未被 Kit 排除；新测试先准备再提出方案。检查命令或配置内容在提出后发生变化，需要修订再确认，不能在 `started` 后替换命令再登记为完成。

用户选定检查或已经接受运行策略后，`run-checks --check-id ...` 先核对冻结配置，再调用可信 Kit 实际运行选中的配置，复核报告并记录结果。每份选中配置的全部步骤都会运行；地图中的 `steps` 指定必须具备通过证据的步骤，不是命令筛选器。运行前检查实际命令和权限；CLI 不提供操作系统沙箱，项目测试可以写文件、访问网络或调用其他程序。

也可用项目已有流程先运行 Kit，再用 `verify --check-id ... --receipt ...` 核对相应检查。无 `--check-id` 的 `verify` 保存整体报告核对，不会把所有模块标为通过。报告应来自真实 Kit，不自行生成具有 `passed` 的 JSON 冒充验收。

覆盖核对检查真实报告的配置、必需步骤和声明输入是否对应计划，同时要求至少一个 `tap` 或 `checks` 行为步骤提供非空证明；只看退出码的 `exit` 步骤不能单独作为模块验收。它仍不能证明命令语义、测试充分性或业务需求全部满足；执行者还需核对实际测试内容。

## 状态与交付

按本次变更区分未配置、未检查、部分检查、通过、失败和需重新检查。未配置不等于通过；检查过一部分也不等于全部覆盖。通过绑定具体方案、配置和源码；地图更新、输入或报告变化可能使旧结果不再适用。

`status` 不运行 Kit，显示的是保存的事件和本地指纹比较。历史通过保留，但沿用前仍需 `verify` 复核真实报告。`delivery_ready` 要求所有必需检查通过，必需模块的相关已配置接口检查也全部通过；任何已执行检查失败或过期都会阻止已有门槛满足。没有必需规则时为 `null`。它只表示本次已配置证据条件，不能拿它宣称整个项目通过。

没有 Kit、没有有效配置或测试无法运行时，保存观察、失败原因与待验项；不把这些替代为 Kit 通过。交付说明同时列出实际验证范围和未覆盖部分。
