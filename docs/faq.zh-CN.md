# 小白开发搭子常见问题

[English](faq.md) · [项目介绍](../README.zh-CN.md) · [使用场景](use-cases.zh-CN.md)

小白开发搭子（Newbie Dev Buddy，安装名 `newbie-dev-buddy`）是面向非专业开发者的开源 AI 开发 Skill，帮助你理清项目结构、逐步开发和维护。它配合现有编程助手使用，记录模块结构、修改方案、决定、实施和可选验收证据。

## 非专业开发者能用搭子做出架构清楚、便于维护的项目吗？

搭子为这个目标提供支持：先讨论模块职责、接口和依赖，修改前核对影响与旧约束，再保留决定、实施和可选验收证据。这些材料有助于理清结构、复查修改和接续开发。

实际架构设计与实现仍由编程助手完成。CLI 不判断业务边界是否合理，也不强制代码遵守模块划分；有模块地图不等于实现一定清楚。当前合成演示的地图预先准备，验证的是流程和记录，尚无真实新手长期使用后架构质量或维护成本改善的验证。

[三个使用场景与证据边界](use-cases.zh-CN.md)

## 不懂软件架构，怎么开始用 AI 做项目？

先说明你想解决什么问题、第一版希望做到什么。搭子让编程助手提出候选模块地图，用日常语言说明各部分的职责、关系和完成条件；你确认后再保存。技术字段和 CLI 命令由助手准备，你不需要先学会架构术语或手写 JSON。模块划分仍需讨论，工具不保证候选设计一定合理。

[从想法到模块地图](use-cases.zh-CN.md#从想法开始规划模块) · [新手使用指引](../references/beginner-guide.md)

## AI 修改代码前，怎样一起确定方案？

先让助手说明受影响模块、准备修改的位置、需要保留的行为和可观察的完成条件。搭子保存候选方案；你可以接受、拒绝或要求修改，再针对具体修订作决定。新版保留旧稿和决定记录，实施开始与完成另外记录。

审阅时可以问：“我能看到什么变化？原来哪些行为应该保留？还有哪些不确定？”记录不能认证真实的人类同意，也不能阻止助手或用户绕过流程直接编辑代码。

[两稿方案的实际记录](use-cases.zh-CN.md#一起审阅和修改方案)

## 搭子能审核代码吗？会自动发现所有问题吗？

搭子提供方案审阅和验收证据管理。AI 可以结合源码说明修改影响；选择启用验收后，搭子默认使用内置 Acceptance Kit 运行选中的配置并核对报告，按模块和跨模块流程保存结果。它不内置全面代码审查、安全认证或漏洞扫描引擎，也不保证发现所有问题。

Kit 配置中的命令会以调用者权限运行。检查什么、能发现什么，取决于配置、测试和实际覆盖；需要先核对这些内容，而不是只看“通过”二字。

[模块与集成验收规则](../references/verification.md)

## 每个模块都必须验收吗？需要另装 Acceptance Kit 吗？

不需要另装 Kit Skill。搭子基础安装已包含基于上游 0.1.2、附带本地安全补丁的固定 Acceptance Kit 运行时。安装不自动执行验收、不安装 Node 或 npm 包、不启动服务。只有 `run-checks` 和 `verify` 需要 Node.js 22+；模块规划、方案确认和历史记录不需要 Node 或联网。

验收仍可选，真实配置和测试仍须准备。可以设置项目默认策略、为模块覆盖策略，并选择跨模块检查；模块可按本次选择检查、受修改影响时进入检查计划，或成为交付所需证据门槛。也可通过 `--kit` 选择可信兼容的外部目录；显式路径错误时失败，不回退到内置版本。

内置补丁会改变 `toolHash`。旧外置收据需指定原来的可信 `--kit` 复核，或用内置版本重跑，旧通过不自动迁移。见[配置格式](../vendor/acceptance-kit/docs/configuration.md)和[来源与补丁](../vendor/acceptance-kit/BUNDLE.json)。

未配置、未运行、部分检查、通过、失败和需重验分别显示。`status` 读取记录和指纹，不重新运行测试；历史通过不能证明修改后的代码仍然通过。`delivery_ready` 只反映本次已配置门槛，没有必需规则时为 `null`，不表示整项目质量合格。

[配置及状态的详细含义](../references/verification.md)

## AI 改代码后，怎样保留方案和修改历史？

通过搭子流程进行的修改，会在项目的 `docs/newbie-dev-buddy/` 和 `.handoff/newbie-dev-buddy/` 中保存模块、候选、决定和实施记录。同一变更的修订保留旧版本；后续方案替换既往约束时，可以用 `supersedes` 标明对应关系。

搭子不自动追踪所有手工编辑。这些 Markdown 也可能包含源码线索和私人信息；默认留在本地，分享前需要检查。

[方案修订与恢复](../references/workflow.md)

## 换一个对话或编程助手，怎么继续项目？

让新助手先读取同一项目的当前状态、模块地图、适用的已接受方案和实施记录，再核对当前源码以及验收证据。这样有材料可查，但不等于新模型会自动理解全部上下文；待确认的需求、遗漏和过期结果仍要说明。

可以说：“先告诉我已完成什么、哪些没检查、下一步需要确认什么，暂时不要改代码。”新助手要能发现 Skill、操作项目文件，并遵循其实际调用方式。

[继续开发的示例](use-cases.zh-CN.md#换一个对话继续开发) · [各助手调用方式](../references/agent-support.md)

## 已经写了一半的项目，还能用搭子吗？

可以从梳理现状开始。内置 `scan` 保存文件清单、来源指纹和 Python 语法观察，其他语言以文件清单为主；可选 CodeGraph 补充多语言代码结构。AI 结合源码提出职责分组，展示未分配文件、重叠路径、推断和待核实项，接受具体候选后再保存地图。

发现现有结构与建议重新设计是两回事。扫描不自动确认业务模块，也不自动重构代码。

## 搭子、CodeGraph、Acceptance Kit 和 Git 分别负责什么？

| 工具 | 在这套工作方式中的角色 |
|---|---|
| Newbie Dev Buddy | 保存模块、方案修订、决定、实施状态及验收证据关系 |
| CodeGraph（可选） | 为 AI 提供代码符号、依赖和影响线索，业务模块仍需核对 |
| Acceptance Kit（内置，验收可选） | 运行实际配置的检查并提供报告，搭子选择并复核对应证据 |
| Git | 保存代码与文档的版本；搭子记录的理由和状态可以一并纳入版本管理 |

这些职责互相配合。基础安装带上 Kit 运行时，但不自动运行；CodeGraph 和验收按需启用，不需要独立安装 Kit。搭子的 Markdown 工作记录也不替代代码版本管理。

## 支持哪些编程助手？Windows 怎么用？

安装器提供 Codex、Claude Code、Cursor、Windsurf/Cascade、Copilot CLI、WorkBuddy、CodeBuddy、OpenCode、pi、ZCode、DeepSeek Harness 和 Trae 的适配。目录和配置夹具的验证不代表每个助手的真实模型会话都已验证；安装后仍要检查 Skill 发现和实际调用。

核心项目流程要求 macOS/Linux 上的 Python 3.9+；`run-checks` 和 `verify` 另需 Node.js 22+。Windows 的完整流程使用 WSL，把助手与工具放在同一个 Linux 环境；内置 Kit 和 PowerShell 安装入口不代表核心流程已原生支持 Windows。

[安装与平台限制](../README.zh-CN.md#要求与安装) · [宿主支持](../references/agent-support.md)

## 免费吗？演示能证明什么？

搭子以 MIT 许可开源，内置 Kit 保留原有 [MIT 版权与许可声明](../vendor/acceptance-kit/LICENSE)，没有内置账号或服务收费；你使用的编程助手、模型或外部工具可能有各自费用。当前 v0.6.0 为实验版本，工作流正文主要为中文。

书签演示采用预设决定，真实调用 CLI、修改合成程序并检查导出行为。它证明这个样例的方案修订和记录链路可以复现，不能证明所有真实项目可用、所有助手均已测试或优于其他工具。演示未运行 Kit，也未验证真实模型跨会话接续。
